启动、Prism、依赖注入与退出

一路跟到主窗口

  1. Company.Shell/Directory.Build.props 和 Company.Shell.csproj 根据解决方案配置共同选出产品。Company.Shell/Program.cs 通过编译条件选择对应 App，以 STA 启动 WPF，加载资源并调用 Run()。源码目录中的两个 Shell 随选定产品被宿主包含，输出分别是 Company.PlcHmi.Shell.exe 与 Company.FlyScan.Shell.exe。
  2. 应用的 App 继承 PrismApplication。PLC 分支通过模块目录发现部署的业务模块，Composition 注册 PLC 服务、账户仓库、授权策略和历史实现。飞拍分支在 RegisterTypes 显式注册模拟机和各页面服务，CreateShell 解析窗口，窗口构造函数得到这些依赖。
  3. PLC 的菜单命令调用 RegionManager.RequestNavigate，目标内容进入 WorkspaceRegion。Region 是窗口预留的视图位置。飞拍主窗口用页签、显式绑定和共享页面事件实现导航，便于在同一视觉界面下装配仿真数据。

DI 与反射分别发生在哪里

DI 表示依赖由外部提供。构造函数写 IUserAccountService，调用方使用接口，用哪个实现由装配决定。RegisterSingleton 表达容器范围的共享实例，RegisterInstance 则注册已经创建的实例。两者的创建时机和资源所有权都值得追踪。DependencyExtension 用 Assembly.GetTypes() 和服务标记筛选可注册类型，属于启动装配上的反射。普通业务方法依旧通过对象和接口调用。

PLC 后台如何启动和结束

ApplicationLifecycle 统一编排启动步骤。这里的顺序可用「先准备操作入口，再恢复历史与消费者，再启动 PLC 运行」记忆。停止使用独立登记的排序，先收尾操作入口、再停采集/连接、再完成历史收尾。后台 Running 表示启动编排已完成；设备是否联机、PLC 值是否有效、日志是否成功入库各有状态。窗口最小化到托盘时继续后台运行，退出时则等待协调器清理。

重复调用共享同一个启动或停止任务。启动中途失败会回收已尝试步骤，后续重试清理会识别已完成的步骤。等待方取消可以结束自己的等待，协调器仍负责清理过程。FlyScan 的仿真窗口则停止自己的计时器，释放工作流、模拟机和 SQLite 连接，有独立的应用生命周期。

WPF 性能怎么查

DataGrid 可启用行/列虚拟化并回收容器，减少长列表需要创建的可视对象。表的滚动容器、布局约束和模板复杂度决定虚拟化能否有效工作。数据虚拟化则要看分页、按需读取或限量查询。优化时先分开观察查询、绑定、布局和渲染，再用可视化树核对元素个数。当前离线基准包含绑定与离屏布局，GPU 渲染和实机帧时间是另外的观测目标。

一次刷新原来做什么，现在做什么

旧路径每次读取整个 observations，重建活动和已关闭的报警、切分采集缺口，最后实时页只取仍活动的记录。新实现把活动报警保存在 _activeAlarms，写入成功后推进内存状态，稳定心跳扩展已知区间。启动时从最近一条在线且全部报警解除的记录开始恢复后续活动状态；缺少这样的记录时需要回放历史。ApplyObservation 让历史重建和实时推进使用同样的规则。

以 UTC 08:00:00 的活动报警为例，连接断开前确认了两秒，08:00:08 重连后又确认了一秒，那么已确认时长为三秒，08:00:02 至 08:00:08 是这次断线缺口。缺口影响时长的可信边界。多个报警的时长可能重叠，所以累计报警时长与设备停机时长是不同指标。本版在 SQLite 采样写入失败后中断会话连续性。下一次成功采样另开区间，失败期间作为未知缺口处理。

public ScanLiveAlarmReport LiveAlarms(DateTimeOffset through)
{
    var online = Online;
